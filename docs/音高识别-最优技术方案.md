# 音高识别：当前最优技术方案

> **本文整理「对标 Flowkey 体感」时，开源世界里当前最好怎么做。**  
> 配套：[音高识别.md](./音高识别.md)（现状实现）、[前沿Idea-本地实时一条龙.md](./前沿Idea-本地实时一条龙.md)（优先级）、[产品定位-一条龙体系.md](./产品定位-一条龙体系.md)。  
> 锁定：2026-09-20（调研结论；未授权前不自动开战役拧常量）

---

## 0. 一句话

**没有「一个开源模型 = Flowkey」。**  
当前最优是分层方案：

> **听音用 Basic Pitch（三端统一）→ 判定用期望音条件化 + Wait → 边沿用 onset/再击 → 示范用回声隔离 → 成谱可另上更准离线引擎；全程可测。**

Flowkey 赢在「带谱听 + 十年脏活」，不是神秘超大模型。开源里也应对齐这条路。

---

## 1. 问题拆开（别混赛道）

| 赛道 | 目标 | 延迟量级 | 开源「当前最强」 |
|------|------|----------|-----------------|
| **跟弹听音（主战场）** | 多音、近实时、能嵌 App | 约 0.15–0.4s（产品），理想冲 &lt;100ms | **Basic Pitch**（工程）；研究向 **rtt / Mobile-AMT** |
| **严格实时交互** | 按下几乎无感 | ≤30ms（论文定义） | **huispaty/rtt**（ISMIR 2025，基线） |
| **离线成谱** | 音符 F1 最高 | 秒～分钟 | **Transkun** / ByteDance 高分辨率转录 |
| **单音实时** | 旋律 / 调音 | &lt;10ms 可 | **PESTO** |
| **跟谱推进** | 对了才走、少误推 | 与听音同级 | **Matchmaker** 思路 + 自研 Wait |

PianoFlow 主路径 = **跟弹听音 + 跟谱推进**；成谱是第二条龙，不要用离线 SOTA 硬塞跟弹。

## 2. 推荐总架构（当前最好）

```
麦克风 PCM
    │
    ├─ RMS / 静音门
    ├─（可选）spectral flux onset
    │
    ▼
┌───────────────────────────────────────┐
│ 多音主引擎：Basic Pitch ONNX（三端统一） │
│ 滚动环 ~2s @22.05k · hop ~30ms        │
│ 忙时只留最新 hop · tail 偏新帧         │
└───────────────────────────────────────┘
    │ 88-bin / active MIDI 集合
    ▼
┌───────────────────────────────────────┐
│ Score-conditioned 解码（关键升级）        │
│ × waitingFor 及邻域 prior              │
│ × onset 门 · 泛音抑制                  │
│ 逐步收回「全局 ±1 放水」                 │
└───────────────────────────────────────┘
    │ noteOn / frame
    ▼
┌───────────────────────────────────────┐
│ Wait / 和弦完备判定                     │
│ GuideRetriggerGate · cue 回声抑制       │
│ Perfect/Good · 误推/漏推仪表            │
└───────────────────────────────────────┘
```

**回退链（保留）：** Basic Pitch → SwiftF0 → YIN（与现状一致）。  
**MIDI：** 可选增强，不作麦克风主路径（产品定位已定）。

## 3. 各层选型说明

### 3.1 听音主引擎 → 继续 Basic Pitch，并三端对齐

| 项 | 结论 |
|----|------|
| **为何是最优** | 开源里唯一同时满足：多音、体积小（~230KB）、Apache-2.0、ONNX/TS、可上手机 |
| **现状** | Windows 已主用；Android 仍 Poly-YIN → **体感短板在端，不在论文** |
| **动作** | Android / Web 与 Windows **同一 BP + 同一 noteOn/门闩语义** |
| **不要做什么** | 不要为了「更新」换成 Transkun/CREPE 当跟弹主引擎 |

**参考文献：** Bittner et al., *A Lightweight Instrument-Agnostic Model for Polyphonic Note Transcription and Multipitch Estimation*, ICASSP 2022. https://arxiv.org/abs/2203.09893  
**仓库：** https://github.com/spotify/basic-pitch

### 3.2 判定层 → Score-conditioned（比换模型更划算）

Flowkey 体感的核心不是「听出所有音」，而是：

> 在谱面告诉我下一组该是什么的前提下，你弹没弹对？

| 现状 | 最优方向 |
|------|----------|
| 先听全集，再 ±1 映射到期望 | BP 概率 × `waitingFor` prior 再判决 |
| 全局放宽掩盖估偏 | 仅期望邻域 soft-match，逐步收紧 |
| 纯集合完备 | 可借鉴 OLTW/HMM 短 horizon（Matchmaker） |

**参考文献：** Matchmaker — *An Open-Source Library for Real-Time Piano Score Following…*, ISMIR 2025. https://github.com/pymatchmaker/matchmaker

### 3.3 边沿 / 连击 → Onset 融合

| 现状 | 最优方向 |
|------|----------|
| lock / emitted / reedge 启发式 | spectral flux（或 aubio 式）onset × 多音结果 |
| 同音再击、踏板延音脆弱 | onset 触发 re-edge；无 onset 的持续电平不推进 |

经典工具：aubio / Essentia（onset）；不必替换主引擎。

### 3.4 示范音隔离 → 从时间窗走向「已知泄漏」

| 现状 | 最优方向 |
|------|----------|
| `echoSuppress` + quiet gap（常量已冻结） | 有 Fail 证据后再开：cue MIDI 自适应抑制、耳机/外放分策略 |
| — | 长期：以 guide 波形为参考的轻量 AEC |

**纪律：** 无仪表盘、无 Fail，不拧 `quiet` / `hop` / `echoSuppress`（见战役外 backlog）。

### 3.5 延迟上限研究（观察，不立刻替换主引擎）

| 项目 | 定位 | 与我们关系 |
|------|------|------------|
| **huispaty/rtt**（ISMIR 2025） | &lt;30ms 因果钢琴转录基线 | **下一世代候选**；先做对照评测，再谈替换 BP |
| **Mobile-AMT**（EUSIPCO 2024） | 手机 online 多音 + 野录音增强 | 架构/增强可借鉴 |
| **Streaming Piano Transcription**（2025） | 分离 onset/offset decoder，~380ms | 准度参考；延迟偏大 |
| **online_amt**（2020） | 早期 streaming 示范 | 历史对照 |

**参考文献：**

- Hu et al., *Exploring System Adaptations for Minimum Latency Real-Time Piano Transcription*, ISMIR 2025. https://arxiv.org/abs/2509.07586 · https://github.com/huispaty/rtt  
- Mobile-AMT, EUSIPCO 2024. https://eurasip.org/Proceedings/Eusipco/Eusipco2024/pdfs/0000036.pdf  
- *Streaming Piano Transcription…*, 2025. https://arxiv.org/abs/2503.01362  

### 3.6 离线成谱（第二条龙，勿混入跟弹）

| 引擎 | 用途 |
|------|------|
| Basic Pitch（现有 `audio_to_practice_draft.py`） | 默认：快、本地、练习用谱 |
| **Transkun**（可选上限） | 要更准的本地成谱时再评估 ONNX/体积 |
| Demucs 等分离 | 可选前处理，服务成谱而非跟弹 |

**参考文献：** Yan & Duan, Transkun / Semi-CRF, ISMIR 2024. https://arxiv.org/abs/2404.09466 · https://github.com/Yujia-Yan/Transkun

### 3.7 单音辅路（已有，保持）

SwiftF0 / YIN 作 BP 失败回退；调试可用 PESTO 作对照（单音实时强，不撑和弦）。

**参考文献：** PESTO, TISMIR. https://transactions.ismir.net/articles/10.5334/tismir.251

## 4. 明确不采用 / 降级采用

| 方案 | 原因 |
|------|------|
| 抄 Flowkey 源码 | 闭源；公开仓只有基建/面试题 |
| 云端大模型教琴 / 云端听写 | 违反「本地实时一条龙」 |
| CREPE 作多音主引擎 | 单音；偏重 |
| Transkun / ByteDance 作跟弹主路径 | 非因果 / 过重 / 延迟不合 Wait |
| 只拧 suppress 常量冲体感 | 已冻结；无 SLO 会回归抖动 |
| MIDI 取代麦克风主路径 | 丢掉原声钢琴用户；可做 Pro 选项 |

## 6. 建议验收数字（可后标定）

对标「Flowkey 级可用」，不要对标论文 F1：

1. **无示范**：固定梯度曲目，误推进 &lt; 2%，漏推进 &lt; 5%，p95 按下→推进 &lt; 300ms  
2. **有 soft cue**：误推进不明显恶化（如 &lt; 2×）  
3. **Android ≈ Windows**（同引擎同语义）  
4. **≤4 音和弦**：完备判定稳定  
5. **同音再击**（无踏板）：可重复触发

## 8. 对外可说的一句

> 我们不追云端大模型，跟弹主引擎继续用开源最成熟的轻量多音 Basic Pitch，并在本地把「带谱判定、onset、示范隔离、可测延迟」做成产品级闭环；更准的离线转录只服务成谱，更激进的 &lt;30ms 因果模型先对照、有数据再换代。
